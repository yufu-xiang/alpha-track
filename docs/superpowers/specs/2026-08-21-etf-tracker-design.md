# 台股 ETF 績效排行與投資追蹤網站 — 設計規格

- 日期:2026-08-21
- 專案代號:alpha-track
- 狀態:已實作；本文保留設計脈絡，實際契約以 `docs/json-contract.md` 為準

## 1. 目標與範圍

建立一個**個人用**的台股 ETF 觀測工具,核心是「全市場 ETF 多期間績效排行」,
並附帶自用的投資組合追蹤。

### 已確認的前提

| 項目 | 決定 |
|---|---|
| 使用對象 | 只給自己用的個人工具,不做帳號系統 |
| 資料即時性 | 每日收盤後更新,不做盤中即時報價 |
| 技術棧 | Python 抓資料與計算 + TypeScript 前端 |
| 架構 | 靜態預算:Python pipeline → SQLite → 匯出 JSON → 純靜態前端 |
| 部署 | GitHub Actions 每日排程 + GitHub Pages,零伺服器成本 |

### MVP 範圍

1. 多期間績效排行榜(核心)
2. 投資組合追蹤(含 XIRR)
3. 折溢價監控 + ETF 檔案
4. 風險指標與多檔比較
5. 指標詞典(每個指標附「是什麼/怎麼算/怎麼看/陷阱」說明)
6. 理財工具組(退休提領、蒙地卡羅回測、定期定額試算等,見第 7 節)

### 第二階段(不在本次範圍)

- 配息中心 UI(除息日曆、填息天數統計)
- 警示通知

### 明確不做

參考站台 jacksu.tw 的「股市投資工具」多數項目**不納入本專案**:
美股行情與排行、13F 持倉、籌碼分析、月營收、法說會行事曆、
恐懼貪婪指數、原物料價格、上市公司薪資。

理由:每一項都是獨立的資料工程(新來源、新清洗、新排程),
且與「台股 ETF」這個主題無關。納入會使專案規模膨脹數倍。
僅採用現有 pipeline 已能支撐的少數項目(見 §7.2)。

註:**配息「資料」第一版就要抓**,因為它是含息報酬驗證的基礎;
第二階段指的是配息的專屬 UI 尚未建置。

## 2. 架構

```
Python pipeline (GitHub Actions 每日排程)
  ├─ TWSE OpenAPI    → 上市 ETF 收盤與基本資料
  ├─ TWSE MIS        → 當日預估淨值、折溢價與規模
  ├─ TPEx OpenAPI    → 上櫃 ETF
  ├─ Yahoo Finance   → 還原權值歷史股價(歷史回補)
  └─ FinMind         → 配息紀錄、價格備援
        ↓
  SQLite(歷史真相來源,累積式)
        ↓  計算層:各期間含息報酬 / MDD / 波動度 / Sharpe / Beta
        ↓
  匯出 JSON  →  Vite + React 靜態網站
                 投資組合存 localStorage(可匯出備份)
```

### 為何選靜態預算

資料本質是「每日更新一次、更新後不再變動」,與靜態化天然對齊。
250 檔 ETF 的排行摘要 JSON 約 200–300 KB,篩選排序在瀏覽器內是毫秒級。
零伺服器代表零維運,這對個人專案的存活率影響大於任何單一功能。
SQLite 會保留,日後若需要動態查詢可再往上疊 API 層,資料模型不必改動。

## 3. 資料層

### 3.0 實作第一步:資料源勘查(必要前置)

**不得憑記憶寫死任何 API endpoint。**
第一項工作是撰寫勘查腳本,實際呼叫各來源,記錄:

- 哪些端點確實可用
- 實際回傳欄位與型別
- 歷史可回溯深度
- 限流政策與配額

產出寫入 `docs/data-sources.md`,**依實測結果定案 schema**。
本規格中的欄位設計是預期值,以勘查結果為準。

### 3.1 資料源分工

| 來源 | 負責資料 | 選用理由 |
|---|---|---|
| TWSE OpenAPI | 上市 ETF 每日收盤與基本資料 | 官方、免金鑰、權威 |
| TWSE MIS | 收盤後預估淨值、折溢價、基金規模 | 當日快照，無歷史查詢，由 SQLite 逐日累積 |
| TPEx OpenAPI | 上櫃 ETF(部分債券型) | 上櫃標的 TWSE 查不到 |
| Yahoo Finance | 還原權值歷史股價 | 唯一能低成本取得長期含息報酬的來源 |
| FinMind | 配息紀錄、價格備援 | 用於交叉驗證還原股價正確性 |

**Yahoo 僅用於歷史回補**,每日增量以官方 TWSE/TPEx 為主。
如此即使 Yahoo 中斷,每日更新仍持續,僅暫時無法新增歷史回補。

歷史回補深度:**該檔有多少抓多少**(0050 可回溯至 2003 年)。

### 3.2 ETF 分類

官方 API 不提供「市值型/高股息/債券/主題/海外」分類,需自行維護。

**程式判定(確定性規則,依官方代號規範):**

- 結尾 `B` → 債券型
- 結尾 `L` → 槓桿型
- 結尾 `R` → 反向型

**人工對照表 `config/etf_categories.yaml`:**

```yaml
0050:   { name: 元大台灣50,       category: 市值型,   region: 台灣 }
0056:   { name: 元大高股息,       category: 高股息,   region: 台灣 }
00662:  { name: 富邦NASDAQ,       category: 海外指數, region: 美國 }
```

約 150 檔現股型 ETF 需一次性建表,新掛牌時補行。

**不使用名稱關鍵字自動分類。** 台股實例顯示此法不可靠:

- `00915`、`00918` 名稱高度相似但選股規則差異大
- 「台灣」二字橫跨多種類型,無鑑別力
- `00713 元大台灣高息低波` 的名稱看不出它另有低波動因子疊加

改依 TWSE 官方 ETF 清單的**標的指數**判定 —— 那是基金投資範圍的權威敘述,
不是行銷名稱。主動式 ETF 與上櫃 ETF 取不到標的指數,只能依名稱,已個別標註。

分類錯誤會直接汙染排行榜的可信度,一次性人工建表的正確性划算得多。

**分類優先序(2026-08-25 建表時確立):**

```
資產類別 > 產業/主題 > 收益目標 > 選股方法 > 大盤
```

台股 2022 年後的高股息 ETF 幾乎全部帶因子疊加(動能、低波、價值、成長),
那是業界常態。若「配息 + 任何因子」一律歸因子型,高股息這一類會只剩少數
老基金,把規模最大、最常被比較的 00939、00940、00944 排除在外,反而誤導。
故**收益目標優先於選股方法**;但產業與主題優先於收益,因為產業集中度對
風險特性的主導程度遠高於配息篩選(例:「電子成長高息等權重」歸產業型)。

**追加的分類(原清單無對應者):**

| 分類 | 檔數 | 為何原清單放不下 |
|---|---|---|
| `主動型` | 37 | 依定義無追蹤指數,報酬來源是經理人而非指數 |
| `期貨信託` | 6 | 追蹤黃金、原油、白銀、銅、黃豆、美元指數,不是股票 |
| `多資產` | 3 | 同時持有股與債 |
| `特別股` | 2 | 行為近債券但不是債,股債兩類都放不下 |

未分類處理:pipeline 偵測到未知代號時列入 run report,歸「未分類」,
仍出現在總排行,僅分類篩選撈不到。**不會因未分類而失敗。**

### 3.3 SQLite Schema

| 資料表 | 內容 |
|---|---|
| `etfs` | 代號、名稱、掛牌日、上市/上櫃、分類、發行商、追蹤指數、內扣費用率、是否槓桿/反向 |
| `prices` | 代號、日期、OHLC、成交量、還原收盤價 |
| `navs` | 代號、日期、淨值、市價、折溢價%、基金規模 |
| `dividends` | 代號、除息日、發放日、配息金額 |
| `metrics` | 代號、計算基準日、期間、含息報酬、年化報酬、波動度、MDD、Sharpe、資料是否完整 |
| `benchmarks` | 加權報酬指數日資料,供 Beta 與超額報酬計算 |

### 3.4 Pipeline

五個可獨立執行與測試的階段:

```
fetch → normalize → store → compute → export
```

- 原始回應存於 `data/raw/YYYY-MM-DD/`,除錯與重算不需重打 API
- 全流程**冪等**:同一天重跑任意次數結果一致,不產生重複列
- 槓桿與反向 ETF 預設從排行榜濾除(長期報酬本質上不可與現股型比較),
  保留於資料庫,前端提供開關顯示

## 4. 指標計算

### 4.1 報酬定義

一律使用**含息總報酬**,以還原權值收盤價計算:

```
報酬 = 期末還原價 / 期初還原價 - 1
```

除息當日的價格跳空由還原價自動吸收,無需另加回配息。
`dividends` 表用於**交叉驗證**:若某日跌幅超過 15% 而當天無除息紀錄,
標記為資料異常待人工檢查。

### 4.2 期間定義

用**日曆日**往回推,非交易日數。
「一年」= 基準日往前推 365 天,取當天或之前最近的交易日為起點。
理由:各檔停牌與掛牌日不同,用交易日數會使比較區間對不齊。
基準日固定為全市場最新收盤日。

期間清單:

```
當日 / 一週 / 一個月 / 三個月 / 六個月 / 今年以來 /
一年 / 三年 / 五年 / 十年 / 成立以來
```

「當日」定義為相對**前一交易日**收盤的還原價變動,非日曆前一日。
「今年以來」起點為當年度第一個交易日。

**一年以上才年化。** 三年以上與成立以來同時顯示累積報酬與年化報酬(CAGR);
一年以內僅顯示累積報酬 —— 將一週報酬年化會產生誤導性數字。

### 4.3 資料不足的處理

掛牌未滿該期間的 ETF:

- 該欄顯示 `—`,附掛牌日 tooltip
- **不參與該期間排名**
- 排序時一律置於列表最末(不論升冪或降冪),不與有效數字混排
- 絕不以 0% 或「成立以來」數字頂替

理由:一檔 2024 年掛牌的 ETF 出現在十年榜上會使整份榜單失去意義。

### 4.4 風險指標

| 指標 | 算法 | 最低樣本 |
|---|---|---|
| 年化波動度 | 日報酬標準差 × √252 | 60 個交易日 |
| 最大回撤 MDD | 還原價峰谷最大跌幅 | 60 個交易日 |
| Sharpe | (年化報酬 − 無風險利率) ÷ 年化波動度 | 一年 |
| Beta | 對加權報酬指數迴歸 | 一年 |
| 折溢價 | 當日折溢價%、近 60 日區間、溢價天數佔比 | 20 個交易日 |

樣本不足一律留空,不提供勉強的數字。

### 4.5 兩項已確認的降級

**(a) 無風險利率為設定值。**
Sharpe 需要無風險利率,但免費來源不易取得台灣公債殖利率。
放在 config,預設 1.5%(接近現行台銀一年期定儲),
UI 於 Sharpe 欄位旁標示「無風險利率 1.5%」使數字可被檢驗。

**(b) 追蹤誤差不做,改為對大盤超額報酬。**
追蹤誤差需要標的指數日資料,但台股 ETF 多追蹤各投信自訂指數,
不對外免費提供,硬做只能涵蓋少數幾檔,榜單會殘缺。
改提供**相對加權報酬指數的超額報酬**,資料可得、對所有台股 ETF 成立,
且更貼近實際關心的問題(這檔有沒有贏大盤)。

## 5. 前端

### 5.1 技術

Vite + React + TypeScript，表格用 TanStack Table，圖表以輕量的原生 SVG 元件實作。
250 筆資料在瀏覽器內排序篩選為毫秒級,不需虛擬化或後端查詢。

**撰寫任何圖表程式碼前,先載入 `dataviz` skill。**

### 5.2 頁面

**① 排行榜(首頁)**

- 一列一檔 ETF,預設按一年報酬排序
- 上方期間按鈕列(當日/一週/一月/三月/六月/YTD/一年/三年/五年/十年/成立以來)
- 分類 chips 篩選 + 搜尋框
- 槓桿反向預設隱藏,開關可顯示

**欄位自選:** 表格右上「欄位」選單,列出全部十一個期間(含成立以來)與風險指標
(波動度/MDD/Sharpe/Beta/折溢價),勾選即顯示,存於 localStorage 沿用,
附「回到預設」。預設顯示 `當日 / 一月 / 三月 / 一年 / 三年`。

**連帶規則:** 若點選的期間按鈕對應欄位當前未勾選顯示,
該欄位自動加入顯示 —— 排序一個看不見的欄位會造成困惑。

**② ETF 個股頁**

- 走勢圖(可切期間、可疊加加權報酬指數基準線)
- 各期間報酬與風險指標卡片
- 折溢價走勢圖(台股 ETF 特有,外部網站少見)
- 配息紀錄表
- 基本資料(發行商、掛牌日、規模、內扣費用、追蹤指數)

**③ 比較頁**

最多同時選 5 檔,走勢**標準化為起點 100** 疊圖
(絕對價格疊圖無意義:一檔 200 元與一檔 20 元無法目視比較漲幅),
下方接指標對照表。

**④ 我的組合** — 見第 6 節

### 5.3 資料載入分層

| 檔案 | 大小 | 時機 |
|---|---|---|
| `meta.json` | 幾 KB | 啟動即載入,含更新時間與健康狀態 |
| `rankings.json` | 200–300 KB | 首頁一次載入,含全 ETF 摘要與所有期間報酬 |
| `etf/{代號}.json` | 每檔數十 KB | 個股頁 lazy load,含完整價格序列與配息 |

### 5.4 響應式

排行榜於窄螢幕**凍結代號與名稱欄、其餘橫向捲動**,不拆成卡片 ——
排行榜的價值在於並排比較,卡片化會破壞此價值。
個股頁與組合頁為正常直式響應式。

### 5.5 資料健康狀態列

頁首顯示如「資料更新至 2026-08-20 · 全部正常」
或「資料更新至 2026-08-19 · 3 檔未分類 · 1 檔價格異常」。

理由:資料來自四個免費來源、其中兩個非官方。
個人工具最大的隱患是「不知道今天的數字能不能信」,
此狀態列成本極低但使每次看到的數字都可被信任。

### 5.6 主題

深色/淺色跟隨系統設定。

### 5.7 指標詞典

**問題:** 排行榜上出現 Sharpe、Beta、MDD、折溢價這類名詞時,
使用者常常不知道該怎麼解讀,數字因此變成裝飾而非決策依據。

**做法:** 建立集中的指標詞典 `src/content/glossary.ts`,
每個指標一筆,固定四個欄位:

| 欄位 | 內容 | 範例(Sharpe) |
|---|---|---|
| 是什麼 | 一句話白話定義 | 每承擔一單位風險,換到多少超額報酬 |
| 怎麼算 | 公式 | (年化報酬 − 無風險利率) ÷ 年化波動度 |
| **怎麼看** | 判讀基準 | 1 以上算不錯,2 以上要先懷疑資料或期間太短 |
| 陷阱 | 常見誤用 | 期間越短越容易失真;空頭期間可能為負,此時大小無意義 |

**「怎麼看」是這份詞典的重點。** 知道公式沒有用,
知道「這個數字落在什麼區間算好」才能做決定。

**兩種呈現,同一份資料源:**

1. 指標名稱旁的 ⓘ 圖示,點擊開啟 popover(不是 hover —— 手機沒有 hover)
2. 獨立的「名詞解釋」頁,由同一份資料自動生成完整列表

須涵蓋:年化報酬、CAGR、含息總報酬、年化波動度、最大回撤、
Sharpe、Beta、超額報酬、折溢價、內扣費用率、XIRR、平均成本、
殖利率、填息、蒙地卡羅成功率、安全提領率。

## 6. 投資組合追蹤

### 6.1 資料模型:交易紀錄,非持股快照

```
交易紀錄:類型(買/賣/配息) · 代號 · 日期 · 股數 · 價格 · 手續費 · 交易稅
```

持股快照撰寫較簡單,但無法計算 XIRR —— 年化報酬需要知道每筆資金的投入時點。
同樣 20% 報酬,三年前投入與上月投入意義截然不同。
交易紀錄可推導出持股,反之不行。

### 6.2 計算項目

| 數字 | 定義 |
|---|---|
| 平均成本 | 移動平均法(與台灣券商對帳單口徑一致) |
| 未實現損益 | (現價 − 平均成本) × 持股數 |
| 已實現損益 | 賣出價 − 成本,扣手續費與交易稅 |
| 累計已領配息 | 自配息紀錄累加 |
| 含息總報酬 | (市值 + 已實現 + 已領息 − 總投入) ÷ 總投入 |
| XIRR | 買入為負、賣出與配息為正、期末市值為正,解年化報酬 |

### 6.3 手續費與稅

放在 config 由使用者填寫。券商手續費折扣因人而異
(標準 0.1425%,折扣戶常見六折以下),
ETF 賣出證交稅率與一般股票不同,債券 ETF 另有規定。

**預設值須於實作時查證現行法規後寫入,不得憑記憶填寫。**
稅率錯誤會使所有損益數字系統性偏差。

### 6.4 配息:自動推估 + 可覆寫

系統依持股與除息日自動計算「應領配息」,**標記為推估值**。
不視為事實的原因:實際入帳會扣除匯費與二代健保補充保費,
金額與對帳單不符。每筆推估配息提供編輯,
填入實際入帳金額後轉為確定值。

### 6.5 儲存與備份

存於 localStorage,提供匯出/匯入 JSON。

**已知風險(必須向使用者明示):** 清除瀏覽器資料、換裝置、換瀏覽器,
紀錄即遺失。因此匯出功能為必需品而非加分項:

- 組合頁放置明顯的匯出按鈕
- 超過 30 天未匯出時顯示提醒

日後若需跨裝置同步,僅需替換 storage 層,交易紀錄資料模型不變。

### 6.6 頁面

- 上方總覽數字(總市值、總投入、含息報酬、XIRR、今日損益)
- 中段資產配置圓餅(可切「依標的」或「依分類」)
- 下方交易紀錄表與「新增交易」表單

## 7. 理財工具組

### 7.1 設計原則:計算機與資料的分離

本節工具**絕大多數是純計算**:輸入參數 → 數學運算 → 圖表輸出,
不依賴 pipeline,可獨立開發與測試。這是它們成本低廉的原因。

但本專案有一項參考站台不具備的優勢:**資料庫裡已有全台股 ETF 的真實歷史**。
因此每個試算工具都提供兩種參數來源:

- **假設模式** —— 使用者自填報酬率與波動度(與一般試算工具相同)
- **實據模式** —— 選定某檔 ETF,直接採用其真實歷史報酬與波動度

實據模式幾乎不增加成本(資料本就存在),但使結果有依據而非猜測。
UI 須明確標示當前使用哪一種模式。

### 7.2 工具清單

**理財工具(純計算,不需新資料源)**

| 工具 | 說明 |
|---|---|
| 退休提領計算 | 4% 法則與動態提領策略,計算資產可支撐年數 |
| 退休金蒙地卡羅回測 | 模擬多種市場路徑,輸出退休金不耗盡的成功率(見 §7.3) |
| 單筆 vs 定期定額試算 | 兩種投入方式的結果比較,支援真實 ETF 歷史回測 |
| 股息再投入試算 | 配息再投入與不再投入的長期差異,使用實際配息資料 |
| 融資維持率計算 | 依持股市值與融資金額計算維持率與追繳價位 |
| 財務自由試算(FIRE) | 依儲蓄率與目標支出推算達成財務自由所需年數 |

**採納的股市工具(現有 pipeline 已能支撐)**

| 工具 | 資料來源 |
|---|---|
| ETF 殖利率排行 | 已有的 `dividends` 表 |
| ETF 成交量/流動性排行 | 已有的 `prices` 表 |
| ETF 成分股重疊度分析 | 需額外抓取成分股,列為此階段的唯一新資料需求 |
| 樂活五線譜 / 樂活通道 | 已有的 `prices` 表,以回歸線與標準差通道判斷相對位階 |

**不採納**:見 §1「明確不做」。

### 7.3 蒙地卡羅模擬:必須處理的統計陷阱

**這是本專案最容易產生「自信但錯誤」結果的功能。**

問題:台股多數 ETF 僅有 5 年內歷史。
以 5 年資料模擬 30 年退休期間,統計上無效 ——
會產生一條外觀精美、實則無意義的成功率曲線,
而使用者可能據此做出重大財務決定。

**因應方式,提供兩種模式並明確標示差異:**

1. **歷史 bootstrap** —— 自加權報酬指數的長期歷史(可回溯數十年)抽樣,
   個別 ETF 僅用於調整其相對特性(Beta、超額報酬)
2. **參數化模擬** —— 使用者自訂報酬與波動假設,
   結果須標示「此為假設推演,非預測」

**強制顯示的資訊:**

- 「本模擬基於 N 年歷史資料」
- 當 N < 10 時,顯著警告資料長度不足以支撐長期推論
- 結果一律以區間(如第 10/50/90 百分位)呈現,不給單一數字

**不做的事:** 不提供「建議提領率」這類規範性建議。
工具呈現計算結果,決策由使用者自行判斷。

### 7.4 頁面

理財工具集中於獨立的「工具」分頁,每個工具一頁。
共用元件:參數輸入面板、模式切換(假設/實據)、結果圖表、
以及本工具用到的指標說明(引用 §5.7 的指標詞典)。

## 8. 錯誤處理

**本專案最大風險不是崩潰,是算錯。**
錯誤的報酬率不會拋出例外,它會安靜地產生看似合理的數字並被據以決策。

### 8.1 Pipeline

**① 來源獨立失敗。** 四個來源各自隔離,Yahoo 中斷不影響 TWSE 每日更新,
僅當天無法回補歷史。網路錯誤重試三次指數退避;遇 429 限流則停止等待,不硬打。

**② 絕不用壞資料覆蓋好資料。** 寫入 DB 前的驗證閘門:

| 檢查 | 動作 |
|---|---|
| 價格 ≤ 0 或欄位缺失 | 拒絕該筆 |
| ETF 檔數較前一日少 10% 以上 | **整批拒絕**(通常代表 API 改格式) |
| 單日報酬 \|r\| > 15% 且當天無除息 | 寫入但標記異常 |
| 折溢價 \|x\| > 10% | 寫入但標記(台股確實出現過,不可擋) |

整批拒絕時保留前一日資料,`meta.json` 標記為 stale,前端顯示「資料未更新」。
**寧可看到昨天的正確數字,不要看到今天的錯誤數字。**

**③ 每次執行產出 run report**,寫入 `meta.json` 供前端健康狀態列顯示。

### 8.2 前端

- JSON 載入失敗顯示明確錯誤畫面,非空白表格
- 資料超過三天未更新時,頁首顯著警告
- localStorage 所有讀寫包覆 try/catch(無痕模式會拋例外)
- 組合中含已下市或查無資料的代號時標示,不使頁面崩潰

## 9. 測試策略

採 TDD。測試重心全部押在計算層。

### 9.1 計算層(主戰場)

全部寫成純函式,以手算驗證過的固定資料測試:

- 給定價格序列 → 報酬、CAGR、MDD、波動度、Sharpe 的期望值
- XIRR 以已知現金流對照 Excel `XIRR` 驗證
- 邊界情況:
  - 僅單筆資料
  - 價格全部相同(波動度 = 0,Sharpe 除以零需處理)
  - 期間內完全無交易日
  - 掛牌天數不足該期間
  - 分批買進後部分賣出的移動平均成本序列

**理財工具的計算同樣屬於此層**,測試要求相同:

- 退休提領:資產恰好歸零、提領額超過資產、報酬率為負的序列
- 蒙地卡羅:固定亂數種子下結果須可重現;
  零波動時所有路徑須收斂為同一條確定性曲線(此為最強的正確性檢查)
- 定期定額:首期與末期的邊界、期間內無交易日
- 融資維持率:分母為零、維持率跌破追繳線的臨界值

### 9.2 解析層

以**存下的真實 API 回應**作 fixture,不打網路。
此為 `data/raw/` 快取的第二個用途。

### 9.3 整合測試

以 fixture 執行完整 pipeline,驗證 DB 內容與匯出的 JSON。

### 9.4 前端

元件測試涵蓋排序、篩選、欄位自選、資料不足的顯示。

### 9.5 明確不做的事

**不對真實 API 撰寫自動化測試** —— 會被限流、會 flaky。
改以手動執行的 `check-sources` 腳本,於懷疑資料源變更時執行。

### 9.6 Golden Test(關鍵)

取 0050 一段真實歷史區間,將計算出的含息報酬與公開資料
(投信月報或財經網站)對照,要求誤差在 0.5% 以內。

理由:單元測試只能證明「程式符合我的假設」,
無法證明「我的假設符合現實」。
此測試是唯一能驗證整條鏈路真正算對的機制。

## 10. 已知限制

1. **無盤中即時報價** — 刻意選擇,台股無合規免費即時來源
2. **十年期資料對多數 ETF 不存在** — 台股 250+ 檔 ETF 多為 2019 年後掛牌,
   長期欄位會大量留空,此為誠實呈現而非缺陷
3. **無追蹤誤差** — 標的指數資料不可免費取得,改以對大盤超額報酬替代
4. **Yahoo Finance 為非官方來源** — 可能變更或中斷,故限用於歷史回補
5. **組合資料存於單一瀏覽器** — 無跨裝置同步,依賴手動匯出備份
6. **分類需人工維護** — 新掛牌 ETF 需補對照表,未補則歸未分類
7. **蒙地卡羅的歷史樣本偏短** — 台股多數 ETF 歷史不足 10 年,
   長期退休模擬須改以加權報酬指數的長歷史為基礎,
   且結果僅為情境推演,不具預測效力(見 §7.3)
8. **不提供任何投資建議** — 所有工具僅呈現計算結果,
   不輸出「建議買進」「建議提領率」這類規範性結論

## 11. 建議實作順序

本規格涵蓋的範圍較大,不適合作為單一實作計畫一次做完。
建議切成四個階段,每階段結束時都是一個**可用的東西**,而非半成品:

**階段 0 — 資料源勘查**
撰寫勘查腳本,產出 `docs/data-sources.md`。
這是唯一的阻斷性前置作業:schema 與後續所有計算都依賴實測結果。
輸出是一份文件,不是產品功能。

**階段 1 — Pipeline 與排行榜(最小可用)**
fetch → store → compute → export 全鏈路打通,
前端只做排行榜頁與欄位自選。
完成時你已經有一個每天自動更新的 ETF 績效排行網站可用。

**階段 2 — ETF 個股頁與折溢價**
個股詳情、走勢圖、折溢價走勢圖、配息紀錄表。
Golden test 應於此階段完成(需要完整的個股歷史資料才能對照)。

**階段 3 — 比較頁與投資組合追蹤**
多檔標準化疊圖、指標對照表;交易紀錄、XIRR、配置圓餅、匯出匯入。

**階段 4 — 理財工具組**
退休提領、蒙地卡羅回測、定期定額與股息再投入試算、融資維持率、FIRE;
以及採納的四項股市工具(§7.2)。

排在最後的理由:這些工具的**實據模式**需要階段 1–3 已完成的真實歷史資料。
若提前實作,只能先做假設模式,之後再重寫接上資料,等於做兩次。
指標詞典(§5.7)則隨各階段增量累積 —— 每階段新增的指標,
該階段就補上對應的說明條目,不留到最後補寫。

階段 1 交付後即具備獨立價值,後續階段可依實際使用感受重新排序。
